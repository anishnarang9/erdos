# R4: Arc behavior (USDC ERC-20 interface, gas, size limits)

Date of checks: 2026-11-14, Arc Testnet (`https://rpc.testnet.arc.io`, chainId `0x4cef52` = 5042002, `web3_clientVersion` = `arc/v1`). Only read-only JSON-RPC (`eth_chainId`, `eth_call`, `eth_estimateGas`, `eth_getCode`, `eth_getBalance`, `eth_getBlockByNumber`, `eth_gasPrice`, `eth_feeHistory`, `web3_clientVersion`) plus local forks. Nothing was signed or broadcast. Scripts are in the scratchpad `research` folder (`h.py`, `i.py`, `j.py`, `forkproj/`).

Sources: `https://docs.arc.io/arc/references/evm-differences.md`, `.../contract-addresses.md`, `.../gas-and-fees.md`, `.../tutorials/troubleshoot-with-arc-foundry.md`, the Arc node source `https://github.com/circlefin/arc-node` (commit `6e764023ee6515fe70573e123ed2db912a7207b4`), reth v2.2.0 source, and arc-foundry v0.8.0-4 source.

## Setup facts

- USDC ERC-20 interface: `0x3600000000000000000000000000000000000000` (docs: "Optional ERC-20 interface for interacting with the native USDC balance. Uses 6 decimals."). It is a proxy to implementation `0xC6AD664ac6679F4Ce74e10E91449C93Ec1ae3cA6` (seen in a fork trace; the EIP-1967 slot is not used, slot read returned zero). The implementation is a Circle FiatToken V2 style contract: `name()` and `symbol()` return `USDC`, `version()` returns `"2"`, `decimals()` 6, `isBlacklisted(address)` (selector `fe575a87`) exists and returns 1 for the seeded address.
- The token moves value via the native-coin precompile `0x1800000000000000000000000000000000000000` (18 decimals). ERC-20 balance is the native balance divided by 1e12 (truncated). Per docs, one balance with two views.
- Seeded blocklisted test address (contract-addresses page, "Test addresses for restricted transfer behavior"): `0x70997970C51812dc3A010C7d01b50e0d17dc79C8` (mnemonic index 1). It has a balance on testnet: `balanceOf` = `0xcdd472` (13,489,266 = 13.489266 USDC), `eth_getBalance` = `0xbb337ffc1b4e9324` (18-dec).
- Holders used as `from`: EOA `0x4E42177AB52202Ced872A5EF661dfc4794bB37bF` (largest holder in `https://explorer.testnet.arc.io/api/v2/tokens/0x3600.../holders`, `balanceOf` 231166172643772143 at the time), contract holder `0x0077777d7EBA4688BDeF3E311b846F25870A19B9` (code length 328 hex chars, `balanceOf` 0x390515987847d), and Multicall3 `0xcA11bde05977b3631167028862bE2a173976CA11` as a contract recipient without `receive`.

## (a) transfer / transferFrom, into and out of contracts, blocklisted address

`eth_call` against `latest` (RPC `{"method":"eth_call","params":[{"from":F,"to":"0x3600...","data":D},"latest"]}`), then confirmed on fork with `arc-forge test --fork-url` (R1).

| Call | Result |
| --- | --- |
| `transfer(0xa1, 1)` from EOA holder | returns `0x...01` (true) |
| `transfer(Multicall3, 1)` from EOA holder (contract recipient, no receive) | returns true. ERC-20 USDC can be pushed into a contract that cannot receive native value. |
| `transfer(0xa1, 1)` with `from` = contract holder `0x0077...` | returns true (contract can send). Fork confirms: `Sink` contract receives 5e6 then transfers out 2e6 fine, native `balance` follows. |
| `transfer(BLOCKLISTED, 1)` and `(BLOCKLISTED, 0)` from EOA holder | **reverts** `{"code":3,"message":"execution reverted: Blocked address"}` with standard `Error(string)` data `0x08c379a0...0f426c6f636b656420616464726573730...` ("Blocked address"). A zero amount to the blocklisted address also reverts. |
| `transfer(x, 1)` with `from` = BLOCKLISTED | eth_call returns `{"code":-32603,"message":"Blocked address"}` (the RPC rejects a blocklisted sender before execution). In a fork or local VM with `vm.prank(BLOCKED)` it executes and reverts `Blocked address` (R1 fork test). |
| `transfer(USDC token address, 1)` | reverts `Blocked address` (the token's own address is not a valid recipient). Never send USDC to `0x3600...`. |
| `transfer(address(0), 1)` | reverts `ERC20: transfer to the zero address` |
| `transfer(x, 2**200)` | reverts `ERC20: transfer amount exceeds balance` |
| `transferFrom(H, OTHER, 1)` with no allowance, from `OTHER` | reverts `ERC20: transfer amount exceeds allowance`. Also true when `from == H` (owner calling transferFrom on itself still needs allowance). |
| `transferFrom(BL, OTHER, 1)` with no allowance | reverts `ERC20: transfer amount exceeds allowance` (allowance check comes first) |

Fork results (`arc-forge test --fork-url https://rpc.testnet.arc.io -vv`, all pass):

- `transferFrom` with a real allowance moves funds and decrements the allowance (`approve(sp, 10)` then pull 4 leaves 6).
- `transferFrom` to a blocklisted recipient reverts (`vm.expectRevert`).
- `approve` **from** a blocklisted owner succeeds inside the fork EVM (the log said "blocked owner approve OK"), but `transferFrom` pulling **from** a blocklisted owner then reverts with `Blocked address`. (The live `eth_call` of `approve` from the blocklisted address returns `-32603 Blocked address` only because the RPC rejects blocklisted senders; on chain a blocklisted sender's transactions cannot be included either way.)
- `approve(blocklisted spender, 5)` succeeds (live `eth_call` returns true); blocking only bites when value moves.
- Native value: `address(blocked).call{value:1}("")` returns false on the fork; `address(0).call{value:1}("")` returns false; a fresh EOA returns true. Matches docs ("Value transfer rules").
- Docs: "A value transfer to or from a blocklisted address reverts. An included transaction that reverts on a blocklist check still consumes gas." and the agent note "blocklist reverts consume gas without a receipt".

**Design consequence:** an escrow payout `USDC.transfer(blocklistedProvider, amount)` reverts with a normal `Error("Blocked address")`, catchable with `try/catch` or a low-level `call` (the revert is an ordinary EVM revert, not a halt). A real reverting-payout scenario (S11) can therefore use the real testnet blocklisted address on a fork (`0x7099...79C8`), or locally after `vm.store(0x1800000000000000000000000000000000000001, keccak256(abi.encode(addr, uint256(2))), bytes32(uint256(1)))` under `--network arc`. A mock token is not required, though a mock can still be used for plain-VM tests. Blocklisting applies per address and per transfer (recipient on `transfer`/`transferFrom`, owner on `transferFrom`), including the escrow contract itself if it were ever blocklisted.

## (b) approve semantics, permit, EIP-2612

Live `eth_call` and fork:

- `approve` overwrites. Sequence on the fork: `approve(sp,5)` then `approve(sp,7)` (non-zero to non-zero) succeeds and `allowance` reads 7; `approve(sp,0)` gives 0; `approve(sp, type(uint256).max)` gives max. **No zero-first restriction.**
- **A max allowance is not infinite**: after `approve(sp, max)` and a `transferFrom` of 3, the fork test logged "allowance after pull with max: decremented". Do not assume infinite-allowance semantics.
- `allowance(owner, spender)` (selector `dd62ed3e`) returns 0 for an unset pair. `increaseAllowance` (`39509351`) is callable (live `eth_call` returned true) and `decreaseAllowance` (`a457c2d7`) selector is present in the implementation bytecode.
- EIP-2612 permit **exists**: `DOMAIN_SEPARATOR()` returns `0x361191522483d32a83e70ae7183b4b9629442c13a78bc9921d6f707911c8c6b0`. Recomputed locally with `arc-cast keccak` as `keccak256(abi.encode(EIP712DOMAIN_TYPEHASH, keccak256("USDC"), keccak256("2"), 5042002, 0x3600...0000))` and it matches exactly, so the domain is name `"USDC"`, version `"2"`, chainId 5042002, verifyingContract `0x3600...`. `nonces(address)` returns 0 for the test address. `PERMIT_TYPEHASH` (selector `30adf81f`) returns `0x6e71edae12b1b97f4d1f60370fef10105fa2faae0126114a169c64845d6126c9` (the standard EIP-2612 permit typehash).
- `permit(owner,spender,value,deadline,v,r,s)` (selector `d505accf`) with a bogus signature and expired deadline reverts `FiatTokenV2: permit is expired`: the function is live. The bytes-signature overload (selector `9fd5a6cf`, FiatToken V2.2) is present in the bytecode; my dummy-argument `eth_call` reverted with no reason, so its usability is UNVERIFIED.
- EIP-3009 also exists: `transferWithAuthorization` (`e3ee160e`) reverts `FiatTokenV2: authorization is expired` for zero arguments, `receiveWithAuthorization` (`ef55bec6`) reverts `FiatTokenV2: caller must be the payee`.
- `eip712Domain()` (EIP-5267, `84b0196e`) reverts (absent). `Permit2` also exists at `0x000000000022D473030F116dDEE9F6B43aC78BA3` (contract-addresses page, testnet).
- A real permit signature was not tested (it would need a private key); only the existence, typehash and domain separator were verified.

## (c) eth_estimateGas for calldata to an EOA

Request shape (`to` = `0x000000000000000000000000000000000000dEaD`, `from` = the EOA holder, `data` = n bytes of `0xff`, all non-zero):

```
{"jsonrpc":"2.0","id":1,"method":"eth_estimateGas","params":[{"from":"0x4E42...37bF","to":"0x...dEaD","data":"0xffff...(n bytes)"}]}
```

| Nonzero calldata | `eth_estimateGas` | Intrinsic 21000 + 16n (pre-7623) | EIP-7623 floor 21000 + 40n |
| --- | --- | --- | --- |
| 0 bytes | 21000 | 21000 | 21000 |
| 1 KiB | 62789 | 37384 | 61960 |
| **4 KiB (4096 B)** | **187474** | 86536 | **184840** |
| **16 KiB (16384 B)** | **682895** | 283144 | **676360** |
| 32 KiB | 1343456 | 545288 | 1331720 |
| 64 KiB | 2664579 | 1069576 | 2642440 |
| 128 KiB | 5306824 | 2118152 | 5263880 |
| 256 KiB | 10591314 | 4215304 | 10506760 |
| 512 KiB or more | error `-32003 gas required exceeds allowance (16777216)` | | |

Exactness check: `eth_call` with an explicit `gas` field. For 16384 nonzero bytes, `gas = 676359` returns `{"code":-32003,"message":"intrinsic gas too low"}` and `gas = 676360` succeeds (`"result":"0x"`). For 4096 bytes the boundary is 184839 (fail) / 184840 (ok). So the true minimum for nonzero calldata is **21000 + 40 bytes**, i.e. the Osaka EIP-7623 calldata floor (10 gas per token, 4 tokens per nonzero byte), not the 16 gas per byte of EIP-2028. `eth_estimateGas` returns about 1 percent above the exact floor (682895 vs 676360 at 16 KiB), which is the node's search tolerance, so size the gas limit from the formula plus margin. All-zero 16 KiB estimated `0x2dc52` = 187474 gas (one token per zero byte, floor 21000 + 10 * 16384 = 184840, plus the same tolerance). A 16 KiB pseudo-random payload (65 zero bytes) estimated `0xa63e2` = 681954 vs computed floor 674410.

Cost at the 20 gwei floor: 676360 gas x 20 gwei = 0.01353 USDC (1.35272e16 in 18-dec native units); 4 KiB: 184840 gas = 0.0037 USDC. A sender with no balance still gets an estimate (`eth_estimateGas` does not check funds when no gas price is given; the unfunded sender test returned `0xa6b8f`).

Note the per-transaction gas cap: EIP-7825 (Osaka) caps a transaction at 16,777,216 gas (`2^24`). Requests above that fail in estimateGas with the message above; `eth_call` with `gas` = 2^24 and 2^24+1 both returned `"0x"` (not enforced for `eth_call`). Maximum nonzero calldata by gas alone is (16777216 - 21000) / 40 = about 418,900 bytes (~409 KiB). Block gas limit is 30,000,000.

## (d) Transaction size limit

- **Docs: nothing found.** I fetched all 149 `.md` pages listed in `https://docs.arc.io/llms.txt` and searched for transaction size, input size, KiB, KB, calldata and mempool limits. No transaction or calldata size limit is documented. The only size-like parameter is `--arc.rpc.max-trace-bytes` (default 64 MiB, node operators, tracing only).
- **Source (best evidence):** the Arc execution node (`circlefin/arc-node`, commit `6e764023ee65`) is built on reth `v2.2.0` and builds its txpool validator with `.with_max_tx_input_bytes(ctx.config().txpool.max_tx_input_bytes)` (`crates/execution-txpool/src/pool.rs` line 85). The reth default for `--txpool.max-tx-input-bytes` is `DEFAULT_MAX_TX_INPUT_BYTES = 4 * TX_SLOT_BYTE_SIZE = 128 KiB` (131072 bytes) (`reth` v2.2.0, `crates/transaction-pool/src/validate/constants.rs`). Arc's own deployment config (`deployments/arc_execution.yaml`) sets only `--txpool.nolocals` and `--txpool.max-account-slots=500` and does not override the input-size flag. So the expected limit is **128 KiB for the full encoded transaction** (reth checks the encoded transaction size, so calldata must be somewhat below 131072 bytes). The 16 KiB case is far below it.
- `eth_estimateGas` does **not** enforce that limit: estimates succeeded at 128 KiB, 129 KiB and 256 KiB above (the gas cap bound at 512 KiB, not a size cap). Whether a live node actually accepts a 128 KiB-plus raw transaction was **not** tested (that needs `eth_sendRawTransaction`, which is prohibited here), so the live limit is UNVERIFIED and is only inferred from source. The deployed testnet nodes could in principle run different flags.
- Osaka also adds EIP-7934 (10 MiB block RLP size limit); not relevant at these sizes.
- Practical limits for the settlement design: a 16 KiB payload costs 676,360 gas minimum (4 percent of the 16.78M per-transaction cap, 2.3 percent of a 30M block) and fits the likely 128 KiB pool limit by a wide margin.

## (e) Base fee and 20 gwei minimum

- Docs (`gas-and-fees.md` fee-parameters table): "Minimum base fee 20 Gwei, Floor enforced by the protocol"; maximum 20,000 Gwei; 30M gas per block; EIP-1559 plus EWMA smoothing; base fee goes to the block beneficiary, not burned (evm-differences, "Fee market and block behavior"). `evm-differences.md`: "Transactions with `maxFeePerGas` lower than 20 Gwei are silently dropped by the mempool. They produce no error receipt and never appear in a block." `gas-and-fees.md` common errors list `transaction underpriced`. Set `maxFeePerGas >= 20 gwei`; priority fee 0 is accepted, "a small tip (for example 1 Gwei) can improve inclusion time".
- Source: `arc-node` `crates/evm/src/executor.rs` lines 617-618: `GENESIS_MIN_BASE_FEE = 20_000_000_000`, `GENESIS_MAX_BASE_FEE = 20_000_000_000_000`.
- Live testnet (block 72387259): `eth_getBlockByNumber` gives `baseFeePerGas` = `0x4a817c800` = 20000000000 (20 gwei), `gasLimit` = 30000000, `extraData` = `0x00000004a817c800` (next base fee, 8 byte big-endian, also 20 gwei). `eth_feeHistory(3, latest, [50])` returned `baseFeePerGas` `0x4a817c800` for all four entries, `gasUsedRatio` about 0.007 to 0.023, and priority-fee rewards of `0x1bf08eb00` (7.5 gwei), `0x47868c00` (1.2 gwei), `0x2e90edd00` (12.4 gwei). `eth_gasPrice` returned `0x4c5e52d00` = 20.5 gwei. So the testnet is sitting on the floor and a bound of `maxFeePerGas` = 20 gwei is the minimum that is accepted; a margin above (for example 25 to 30 gwei) is safer if the base fee rises.

## Findings that change or confirm the settlement design

1. **Blocklisted transfers revert normally with `Error("Blocked address")`.** The plan line 40 UNVERIFIED claim is now VERIFIED for ERC-20 `transfer`/`transferFrom` (recipient blocklisted, also owner blocklisted on `transferFrom`, also when amount is 0). S11's reverting-payout scenario can use the real blocklisted address `0x70997970C51812dc3A010C7d01b50e0d17dc79C8` on a fork, or locally via `vm.store` on the NativeCoinControl precompile. A mock is optional, not required. Payout design must still tolerate revert (pull pattern or try/catch) because blocklisting is controlled by Circle.
2. **Permit (EIP-2612) and EIP-3009 exist** on the USDC ERC-20 interface, so a `permit`-then-`transferFrom` flow and signature-based funding are possible. Domain name `"USDC"`, version `"2"`, chainId 5042002.
3. **approve overwrites with no zero-first rule; max allowance is decremented.** Safe to use `approve(amount)` directly; do not rely on infinite approval.
4. **Calldata gas follows the 7623 floor: 40 gas per nonzero byte.** 16 KiB nonzero is 676,360 gas, 4 KiB is 184,840 (minimum; estimateGas reports about 1 percent more). Cost at 20 gwei is about 0.0135 USDC for 16 KiB. Per-transaction cap is 16,777,216 gas.
5. **Size limit unconfirmed on chain:** expected 128 KiB encoded transaction from reth defaults, not documented by Arc and not testable read-only.
6. **USDC can be sent into a contract without `receive`** via ERC-20 `transfer`, but native value to such a contract reverts as usual; and the ERC-20 `transfer` to the token address itself reverts. Native-USDC sweeps stay out of the escrow, as the plan already says.
7. Every USDC transfer emits two Transfer logs (system emitter `0xffff...fffe` in 18-dec and the token `0x3600...` in 6-dec); the escrow's event handling must watch only `0x3600...`.

## UNVERIFIED

- Live acceptance of a transaction over 128 KiB (no sending allowed).
- Real signed `permit` or `transferWithAuthorization` flow (no key).
- Usability of the `permit(..., bytes signature)` overload.
- Behavior of the real blocklist on a mainnet chain id (only testnet checked).
