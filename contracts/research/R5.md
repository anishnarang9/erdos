# R5: Hook interface and exact core ABI

Date: 2026-11-14. Track: T1 (core). Source: Circle's verified `AgenticCommerce.sol` and `IACPHook.sol` (vendored unchanged under `contracts/src/core/src/`). Everything below is read from that source and from the compiled artifact (`out/.../AgenticCommerce.json` `methodIdentifiers`) and cross-checked with `arc-cast sig`/`keccak`. Line numbers refer to `contracts/src/core/src/AgenticCommerce.sol`. The patched copy (`AgenticCommercePatched.sol`) differs only at line 178 (see the end).

## Discrepancies and additions versus Section 2 of the spec

No factual discrepancy in Section 2 or in the Section 6 payload layouts: every statement checked is correct. Things the spec does not say that the hook author should know:

1. **`IACPHook` interface ID is `0x7ff6bc9e`** (R5 result, below).
2. **`setProvider(jobId, provider)` exists** (selector `0xd0fae591`, event `ProviderSet`). It is client-only, Open state only, allowed only while `job.provider == address(0)`, and is **not hooked** and **not `nonReentrant`**. Because the hook's `createJob` after-rule requires `provider != 0`, a job that uses our hook can never reach this path.
3. **`createJob` itself does not require a nonzero provider**; only the hook rule does. `fund` reverts `ProviderNotSet` if it is zero.
4. **`complete` has no expiry check and `submit` has no expiry check in the core.** Only `fund` (`block.timestamp >= expiredAt` reverts `WrongStatus`) and `claimRefund` (`block.timestamp < expiredAt` reverts `WrongStatus`) test time. All time boundaries for submit/release come from the hook. `claimRefund` also works on a `Submitted` job (so a submitted-but-unreleased job is refundable after expiry).
5. **No hook is called before `createJob`.** `createJob` has only an after-hook. `claimRefund` and `setProvider` have no hooks.
6. **`setBudget` is hooked both before and after, with the same `data`.** `fund`, `submit`, `complete`, `reject` are also hooked before and after with the same `data` for both calls (the `data` bytes are built once). The after-hook of each runs at the very end of the function (after state changes, transfers and events).
7. **`reject`**: client while `Open`; evaluator while `Funded` or `Submitted`; any other status reverts `WrongStatus`. It refunds the client if the previous status was `Funded` or `Submitted` and `budget > 0`. The spec says "reject is allowed for the client while Open and for the evaluator while Funded or Submitted", which matches. Note the **client can call `reject` on an Open job**; that triggers our hook callbacks (selector `reject`), which the hook must allow.
8. **Re-entrancy**: `createJob`, `setBudget`, `fund`, `submit`, `complete`, `reject`, `claimRefund` use `nonReentrant` (OZ `ReentrancyGuardTransient`, transient storage, EVM cancun). A hook callback therefore **cannot call any of those on the core** (it reverts `ReentrancyGuardReentrantCall()` `0x3ee5aeb5`). View functions (`getJob`, `jobs`, ...) are fine. `release` calling `core.complete` is not nested, so it works.
9. `fund` uses `job.budget` at call time. After the patch only the client can change the budget, and only in `Open` state, so the Solver cannot front-run `fund` by changing the price.
10. `getJob` returns the whole struct including the `description` string, so it costs more gas than reading fixed fields. `jobs(uint256)` (public mapping getter) returns the same nine fields as a flat tuple.
11. A zero hook is allowed (`whitelistedHooks[address(0)] = true` set in `initialize`), verified by test. A non-whitelisted hook reverts `HookNotWhitelisted()` **before** the ERC-165 check; a whitelisted nonzero hook without ERC-165 `IACPHook` support reverts `InvalidJob()`.
12. The treasury and fee state: `initialize` sets treasury and grants both roles to `admin_`; fees default to 0 (`setPlatformFee`/`setEvaluatorFee` are `ADMIN_ROLE`-gated; `setHookWhitelist` is `ADMIN_ROLE`-gated; `_authorizeUpgrade` is `DEFAULT_ADMIN_ROLE`-gated).

## ERC-165 interface ID of `IACPHook`

```solidity
interface IACPHook {
    function beforeAction(uint256 jobId, bytes4 selector, bytes calldata data) external;
    function afterAction(uint256 jobId, bytes4 selector, bytes calldata data) external;
}
```

| Function | Selector |
| --- | --- |
| `beforeAction(uint256,bytes4,bytes)` | `0xdc08fb1d` |
| `afterAction(uint256,bytes4,bytes)` | `0xa3fe4783` |

`type(IACPHook).interfaceId = 0xdc08fb1d ^ 0xa3fe4783 = ` **`0x7ff6bc9e`**. Checked by the test `test_iacpHookInterfaceId` in `contracts/test/core/Provenance.t.sol` (selectors, XOR, and `type(IACPHook).interfaceId`). The core's check is `ERC165Checker.supportsInterface(hook, type(IACPHook).interfaceId)`: OZ's checker first calls `supportsInterface(0x01ffc9a7)` (must return true), then `supportsInterface(0xffffffff)` (must return false), then `supportsInterface(0x7ff6bc9e)` (must return true). A hook that returns true for everything fails. Mixed-in `supportsInterface` in the hook should return `id == type(IACPHook).interfaceId || id == type(IERC165).interfaceId`.

### Struct and enum

```solidity
enum JobStatus { Open, Funded, Submitted, Completed, Rejected, Expired }   // 0..5

struct Job {
    uint256 id;
    address client;
    address provider;
    address evaluator;
    string description;
    uint256 budget;
    uint256 expiredAt;
    JobStatus status;
    address hook;
}
```

Storage order (for reference): `paymentToken`, `platformFeeBP`, `platformTreasury`, `evaluatorFeeBP`, `jobs`, `jobCounter`, `whitelistedHooks`, `jobHasBudget` (after the OZ upgradeable/transient bases, which use namespaced storage).

## Hook payloads (exact)

`beforeAction(uint256 jobId, bytes4 selector, bytes data)` and `afterAction(...)` are called as `IACPHook(hook).beforeAction(jobId, msg.sig, data)`. `selector` is `msg.sig` of the core function. If `hook == address(0)` nothing is called. `caller` is always `msg.sender` of the core call.

| Core function | selector arg | Hook(s) | `data` encoding |
| --- | --- | --- | --- |
| `createJob` | `0x41528812` | after only | `abi.encode(address caller, address provider, address evaluator)` (core line 158: `abi.encode(msg.sender, provider, evaluator)`) |
| `setBudget` | `0xdd4ae9d4` | before, after | `abi.encode(address caller, uint256 amount, bytes optParams)` (line 180) |
| `fund` | `0xe25ba707` | before, after | `abi.encode(address caller, bytes optParams)` (line 198) |
| `submit` | `0x9e63798d` | before, after | `abi.encode(address caller, bytes32 deliverable, bytes optParams)` (line 219) |
| `complete` | `0xd75bbdf3` | before, after | `abi.encode(address caller, bytes32 reason, bytes optParams)` (line 234) |
| `reject` | `0x41dd26f5` | before, after | `abi.encode(address caller, bytes32 reason, bytes optParams)` (line 273) |

Decode in the hook with `abi.decode(data, (address, uint256, bytes))` etc. These are standard ABI encodings of the parameter tuples, **not** `abi.encodePacked`, and **not** wrapped as a single struct. `optParams` is the raw `bytes` the caller passed. For our protocol (Section 7 of the spec) `fund`'s `optParams` is `abi.encode(bytes32 imageId, bytes32 rulesHash, bytes32 referenceHash)` and `submit`'s is `abi.encode(bytes envelope, bytes seal, bytes32 keyCommitment)`, both decoded by the hook from `optParams`.

State visible to the hook during each callback:

| Callback | Job status | Funds |
| --- | --- | --- |
| `createJob` after | Open, job stored, `budget == 0` | none |
| `setBudget` before / after | Open; budget old / new | none |
| `fund` before | Open | not yet transferred |
| `fund` after | Funded | `budget` already in the core |
| `submit` before | Funded (or Open if budget 0) | escrowed |
| `submit` after | Submitted | escrowed |
| `complete` before | Submitted | escrowed, not paid |
| `complete` after | Completed | already paid out |
| `reject` before | Open / Funded / Submitted | not refunded |
| `reject` after | Rejected | refunded if it was Funded/Submitted |
