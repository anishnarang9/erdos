## `RiscZeroGroth16Verifier.sol`

- `VERSION` (line 59): `string public constant VERSION = "3.1.0"`.
- `SELECTOR` (line 119, `bytes4 public immutable`), computed in the constructor:
  `bytes4(sha256(abi.encodePacked(sha256("risc0.Groth16ReceiptVerifierParameters"), control_root, reverseByteOrderUint256(uint256(bn254_control_id)), verifier_key_digest(), uint16(3) << 8)))`.
  `verifier_key_digest()` hashes the Groth16 verification key baked into `Groth16Verifier.sol`. Value with the constants above: `0xe71e6620` (asserted in our test, and the upstream test `testSelectorIsStable` asserts the same). The test receipt's seal also starts with `e71e6620`.
- Constructor: `constructor(bytes32 control_root, bytes32 bn254_control_id)` (line 115). `CONTROL_ROOT_0`, `CONTROL_ROOT_1` (two reversed 128-bit halves) and `BN254_CONTROL_ID` are immutables.
- `verify(bytes calldata seal, bytes32 imageId, bytes32 journalDigest) external view` (line 145) builds the claim digest with `ReceiptClaimLib.ok(imageId, journalDigest).digest()` and calls `_verifyIntegrity`.
- `verifyIntegrity(Receipt calldata)` does the same with `receipt.claimDigest`.
- Seal layout: 4-byte selector then `abi.decode(seal[4:], (Seal))` where `Seal = {uint256[2] a; uint256[2][2] b; uint256[2] c}`, which is 8 words = 256 bytes. Exact seal length is 260 bytes (the test receipt seal is 260 bytes; asserted in our test). A 259-byte seal and an empty seal both revert (empty seal: slicing `seal[:4]` panics; tested).
- Errors: `SelectorMismatch(bytes4 received, bytes4 expected)` is declared at file level in `RiscZeroGroth16Verifier.sol`. `VerificationFailed()` is declared in `IRiscZeroVerifier.sol` line 195.
- Behavior on tampering (measured here with arc-forge):
  - A changed selector gives `SelectorMismatch(received, expected)`.
  - A changed journal digest or image ID gives `VerificationFailed()` at normal cost.
  - A changed byte in the 256-byte proof part gave `VerificationFailed()` in all 256 low-bit flips and in 5 high-bit flips, but each one burned almost all the gas supplied. Reason: the flipped coordinate is off the BN254 curve, the ecAdd/ecMul/pairing precompile call fails, and a failed precompile call consumes the whole gas it was forwarded (`staticcall(sub(gas(), 2000), 6|7|8, ...)` in `Groth16Verifier.sol` lines 91, 101, 168). The verifier then returns false and reverts with `VerificationFailed()` using the remaining 2000+ gas.
  - Consequence for T3/T4/T5: a `submit` with a garbage seal reverts with `VerificationFailed()` but uses nearly the full gas limit it was given (tests must pass a gas limit, as `verify{gas: 3_000_000}` does in our test; on Arc a 30M limit costs about 0.6 USDC at the 20 Gwei minimum, UNVERIFIED as a fee figure). `eth_estimateGas` for such a call reports a revert, not a number. A seal with right shape but wrong claim (the S6 verdict-0 case, the S5 wrong image ID case) is cheap.

## Upstream mock verifier

`contracts/src/test/RiscZeroMockVerifier.sol` exists (upstream, not under `src/groth16`). Behavior:

- `constructor(bytes4 selector)` stores `SELECTOR`.
- `verify` and `verifyIntegrity` revert with `SelectorMismatch(received, expected)` if the first 4 bytes of the seal differ from `SELECTOR`, and with `VerificationFailed()` unless `seal[4:] == abi.encodePacked(claimDigest)`.
- `mockProve(imageId, journalDigest)` and `mockProve(claimDigest)` return a `Receipt` whose seal is `SELECTOR || claimDigest`.
- So it accepts every correct pair and cannot be told to reject one. It declares its own `SelectorMismatch` error at file level, which clashes by name with the one in `RiscZeroGroth16Verifier.sol` if both are imported into one file.

Our `contracts/src/verifier/MockRiscZeroVerifier.sol` differs on purpose: empty constructor, an `expect(seal, imageId, journalDigest)` setter that registers triples (many allowed), and `verify` reverts with `UnexpectedProof()` unless the exact triple was registered. See that file for details. We did not use the upstream mock because it cannot reject a chosen proof (it accepts any `SELECTOR || claimDigest` seal) and the spec (Section 5) asks for a mock that accepts preconfigured triples.
