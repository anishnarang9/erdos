Today a buyer pays for a deliverable and then checks it. We flip the order: the checks are agreed first, a zero-knowledge proof shows the files pass them, and only then does escrow release the payment and the key to the files.

Define the checks. Prove the work passes.

The Erdos engine compiles the buyer’s rules into a checker. When Arc accepts proof that the delivery passed, escrow releases the payment.

READING THE BRIEF

Agree on
what passes

The buyer specifies the deliverable and approves the checks before funding.

Lock the
reward

The buyer deposits the bounty. Solvers can see the amount and deadline before taking the job.

Prove the
work

The solver submits a proof tied to the encrypted files it prepared.

Release the
payment

Once Arc accepts the proof, settlement pays the solver and publishes the delivery key.

Unlock the
files

The buyer's browser checks the files against the proof, then uses the published key to open them.

System architecture

USDC escrow

The reward stays locked until the proof passes or the buyer can claim a refund after expiry.

RISC ZEROGROTH16 VERIFIER

Built with

Proof engine
The Rust engine compiles the buyer’s rules into a checker. RISC Zero runs it against the delivery and produces a Groth16 proof that Arc can verify.
Escrow and settlement
Solidity contracts based on ERC-8183 hold test USDC on Arc Testnet. After proof acceptance, settlement pays the solver and releases the delivery key.
Build and runtime
Docker provides a repeatable environment for building checkers and generating proofs.
